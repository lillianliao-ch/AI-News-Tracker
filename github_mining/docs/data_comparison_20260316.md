### 四、根本原因分析（已确认）

#### 问题1: Task 17修复的是"假问题"

**2024年contact cache分析**:
- 总条目: 35,846
- `serper::Name` 格式: 17,923条（有3,147条有邮箱）
- `Name::` 格式: 17,637条（**0条有邮箱**）
- 重叠人数: 17,637人（几乎所有`Name::`都有对应的`serper::`）

**结论**: Task 17修复的`Name::`格式兼容性**毫无意义**，因为：
1. `Name::`格式的数据本身就没有邮箱
2. 所有`Name::`的人都已经有`serper::`格式的数据
3. merge_data()优先使用`serper::`，所以`Name::`永远不会被用到

#### 问题2: 缓存数据本身覆盖率就低

**2024年B+级别（7,276人）实际情况**:
- full.json中已有邮箱: 153人（2.1%）
- contact cache中有邮箱: 1,638人（22.5%）
- **merge后理论最大覆盖率: 23.8%**
- **实际DB覆盖率: 19%**

**差距分析**:
- 理论vs实际差距: 23.8% - 19% = 4.8pp
- 这4.8pp的差距可能是：
  - import时的merge逻辑问题
  - 或者--update模式没有正确更新已有记录

#### 问题3: 文档中的"42%"数据来源不明

**文档声称**: 2024 B+可触达率42%

**实际验证**:
- contact cache最多只能提供23.8%的邮箱覆盖
- 即使加上deep cache，也不可能达到42%
- **结论**: 文档中的42%数据可能是：
  1. 统计错误
  2. 或者包含了其他年份的数据
  3. 或者是预期值而非实际值
